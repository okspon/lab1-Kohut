# Лабораторна робота No12
• Тема: Обробка IO/мережевих помилок та патерн Retry.

• Інструмент: .NET SDK, IDE на вибір студента

## Мета
Навчитися обробляти типові помилки вводу/виводу та мережеві помилки за допомогою
блоків try-catch-finally, а також реалізувати патерн Retry для підвищення відмовостійкості
застосунків.

## Теоретичні відомості
• Винятки вводу/виводу: Помилки, що виникають при роботі з файлами, потоками даних
(наприклад, FileNotFoundException, DirectoryNotFoundException, IOException).
• Мережеві винятки: Помилки, що виникають при взаємодії з мережевими ресурсами
(наприклад, HttpRequestException, SocketException).
• try-catch-finally: Базовий механізм обробки винятків у C#.
• Патерн Retry: Стратегія повторних спроб виконання операції, яка може тимчасово
завершитися невдачею.
• Експоненційна затримка: Стратегія збільшення часу очікування між повторними
спробами.

## Хід роботи
У цій лабораторній роботі я реалізувала консольний застосунок мовою C# для демонстрації обробки помилок вводу/виводу 
та мережевих запитів із застосуванням патерну Retry. Я створила класи FileProcessor та NetworkClient, які імітують тимчасові винятки FileNotFoundException та HttpRequestException,

Усе це я продемонструвала у файлі Program.cs, додала короткий висновок,

## ВИСНОВОК ДО КОДУ

Принцип роботи експоненційної затримки полягає у прогресивному збільшенні паузи 
між повторними спробами за формулою `delay = initialDelay * (2 ^ (attempt - 1))`. 
Це дозволяє уникнути надмірного навантаження на мережу або файлову систему під час 
короткочасних збоїв, даючи ресурсам час на відновлення, що значно підвищує відмовостійкість застосунку.

## Контрольні запитання

1. Які типи винятків найчастіше виникають при роботі з файлами та мережею?

При роботі з файлами (I/O) найчастіше виникають такі винятки:
• FileNotFoundException — вказаного файлу не існує за заданим шляхом.
• DirectoryNotFoundException — не знайдено вказану директорію.
• UnauthorizedAccessException — відсутні права доступу до файлу або каталог має атрибут «тільки для читання».
• PathTooLongException — шлях до файлу або його ім'я перевищує максимально допустиму довжину.
• IOException — загальна помилка вводу/виводу (наприклад, файл заблоковано іншим процесом).

При роботі з мережею найчастіше виникають:
• HttpRequestException — виникає при невдалих HTTP-запитах (помилки з'єднання, відповіді сервера з кодами 4xx/5xx).
• SocketException — помилки на рівні сокетів та мережевих протоколів (відсутнє інтернет-з'єднання, невідомий хост).
• TaskCanceledException / TimeoutException — перевищено ліміт часу очікування відповіді від сервера (Timeout).

2. Поясніть принцип роботи патерну Retry. Коли його доцільно використовувати?

Принцип роботи:
Принцип полягає у повторному автоматичному виконанні операції, яка завершилася винятком, визначену кількість разів з паузами між спробами. Застосунок перехоплює помилку у блоці catch, чекає заданий час і знову викликає той самий метод, поки операція не завершиться успішно або не вичерпається ліміт спроб.

Коли доцільно використовувати:
Його доцільно використовувати для обробки тимчасових транзитних збоїв (Transient Errors), які виникають спонтанно та зазвичай зникають самі за короткий проміжок часу (наприклад, короткочасна втрата пакетів у мережі, тимчасове перезавантаження сервісу API або блокування файлу іншим потоком).

3. Як реалізувати експоненційну затримку між повторними спробами?

Експоненційна затримка реалізується шляхом збільшення часу паузи між спробами у геометричній прогресії (подвоєння затримки на кожному кроці).

Формула обчислення:
delay = initialDelay * Math.Pow(2, attempt - 1)

Приклад реалізації в коді:
int delayMs = initialDelayMs * (int)Math.Pow(2, currentAttempt - 1);
Thread.Sleep(delayMs);

Завдяки цьому час очікування зростає прогресивно (наприклад: 400 мс -> 800 мс -> 1600 мс -> 3200 мс), що зменшує навантаження на систему чи мережу під час аварійного стану.

4. Для чого потрібен делегат shouldRetry у допоміжному класі RetryHelper?

Делегат-предикат Predicate shouldRetry потрібен для фільтрації винятків. Він перевіряє тип або властивості помилки і повертає true, якщо помилку варто повторювати, та false, якщо ні.

Це дозволяє повторювати спроби тільки для тимчасових помилок (HttpRequestException, FileNotFoundException) і негайно зупиняти виконання та прокидати виняток далі у випадку фатальних помилок логіки (NullReferenceException, ArgumentNullException), повторювати які немає сенсу.
