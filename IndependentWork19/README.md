# Самостійна робота No19

• Тема: Дизайн винятків і політики retry: теорія та кейси Polly.
• Обсяг: 80 хв (2 академічні години)

## Мета

Опрацювати теорію обробки винятків у .NET (механізм try-catch-finally, власні типи винятків, коли
кидати виняток i коли повертати Result), вивчити патерни відмовостійкості (Retry, Circuit Breaker,
Bulkhead) та бібліотеку Polly, реалізувати практичні сценарії i підготувати звіт.

## Хід роботи

У межах цієї роботи я створила консольний проєкт IndependentWork19, підключила бібліотеку відмовостійкості Polly та реалізувала власний клас винятку TicketBookingException із трьома стандартними конструкторами і бізнес-властивостями 
(EventCode, RequestedSeats, AvailableSeats), продемонструвавши його перехоплення в конструкції try-catch-finally. Крім того, за допомогою сучасного API ResiliencePipelineBuilder я розробила та протестувала три різні сценарії обробки 
збоїв із детальним логуванням: стратегію Retry з експоненційною затримкою та Jitter для платіжного шлюзу, патерн Circuit Breaker зі зміною станів Closed, Open та Half-Open для нестабільної бази даних бонусів, а також комбінацію Timeout + Fallback для сервісу рекомендацій.
За результатами роботи я підготувала звіт у файлі REPORT.md з обґрунтуванням вибору між винятками та підходом Result<T> і завантажила проєкт на GitHub.

## 1. Власний тип винятку (`TicketBookingException`)

Для предметної області **«Онлайн-бронювання квитків»** реалізовано клас `TicketBookingException`, успадкований від `System.Exception`. Він містить три обов'язкові стандартні конструктори (без параметрів, з `message`, з `message` та `innerException`) і спеціалізований конструктор для збереження бізнес-контексту: `EventCode` (код події), `RequestedSeats` (запитана кількість місць) та `AvailableSeats` (залишок вільних місць). У `Main` продемонстровано перехоплення від специфічних винятків (`TicketBookingException`, `ArgumentOutOfRangeException`) до загального `Exception` з обов'язковим виконанням блоку `finally`.

## 2. Реалізовані сценарії відмовостійкості з Polly (`ResiliencePipelineBuilder`)

### Сценарій 1: Retry + Exponential Backoff + Jitter (Платіжний шлюз)
* **Опис проблеми:** Під час виклику зовнішнього платіжного API можливі короткочасні мережеві збої або тимчасова перевантаженість (`HttpRequestException: 503 Service Unavailable`).
* **Обґрунтування стратегії:** Використано `Retry` із максимальною кількістю спроб `3`, експоненційним зростанням затримки (`DelayBackoffType.Exponential`) та випадковою складовою (`UseJitter = true`). Експоненційна затримка дає сервісу час на відновлення, а *Jitter* запобігає одночасному «шторму» повторних запитів від багатьох клієнтів.
* **Фрагмент коду:**
  ```csharp
  var retryPipeline = new ResiliencePipelineBuilder<string>()
      .AddRetry(new RetryStrategyOptions<string>
      {
          ShouldHandle = new PredicateBuilder<string>().Handle<HttpRequestException>(),
          MaxRetryAttempts = 3,
          Delay = TimeSpan.FromMilliseconds(400),
          BackoffType = DelayBackoffType.Exponential,
          UseJitter = true
      })
      .Build();

Опис виводу: Перші 2 виклики завершуються помилкою 503 Service Unavailable, Polly логує кожну повторну спробу з розрахованою затримкою, а 3-й виклик успішно повертає ідентифікатор транзакції.

Сценарій 2: Circuit Breaker (Нестабільна БД бонусної програми)
Опис проблеми: База даних бонусів тимчасово «впала» і кожен запит до неї зависає до таймауту (TimeoutException). Постійні повторні спроби лише погіршують ситуацію та затримують відповідь користувачеві.

Обґрунтування стратегії: Обрано патерн Circuit Breaker (MinimumThroughput = 3, FailureRatio = 1.0, BreakDuration = 1s). Після 3 невдалих запитів вимикач переходить у стан Open і миттєво відхиляє 4-й запит винятком BrokenCircuitException без реального звернення до БД. Після паузи вимикач переходить у Half-Open, пропускає пробний 5-й запит, фіксує відновлення БД і повертається у стан Closed.

Фрагмент коду:
```
var circuitBreakerPipeline = new ResiliencePipelineBuilder<int>()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<int>
    {
        ShouldHandle = new PredicateBuilder<int>().Handle<TimeoutException>(),
        FailureRatio = 1.0,
        MinimumThroughput = 3,
        BreakDuration = TimeSpan.FromSeconds(1)
    })
    .Build();
```
Опис виводу: Запити #1–#3 падають по таймауту, після чого логується перехід Circuit Breaker -> OPEN; запит #4 миттєво відхиляється; після паузи логується HALF-OPEN, запит #5 виконується успішно, і ланцюг повертається у стан CLOSED.

Сценарій 3: Комбінація Timeout + Fallback (Сервіс персональних рекомендацій)
Опис проблеми: Другорядний мікросервіс рекомендацій відповідає занадто повільно (1000 мс), що погіршує швидкість завантаження сторінки для користувача.

Обґрунтування стратегії: Поєднано зовнішню стратегію Fallback та внутрішню Timeout (ліміт 300 мс). Якщо сервіс не вкладається у 300 мс, Timeout скасовує операцію через CancellationToken (TimeoutRejectedException), а Fallback перехоплює цей виняток і повертає заздалегідь підготовлений кешований список популярних подій (graceful degradation).

Фрагмент коду:

```
var fallbackAndTimeoutPipeline = new ResiliencePipelineBuilder<List<string>>()
    .AddFallback(new FallbackStrategyOptions<List<string>>
    {
        ShouldHandle = new PredicateBuilder<List<string>>().Handle<TimeoutRejectedException>(),
        FallbackAction = _ => Outcome.FromResultAsValueTask(cachedEvents)
    })
    .AddTimeout(TimeSpan.FromMilliseconds(300))
    .Build();
```
Опис виводу: Через 300 мс спрацьовує [Polly Timeout], одразу після цього активується [Polly Fallback], і користувач отримує кешовані рекомендації без збою застосунку.

## 3. Коли кидати виняток, а коли повертати Result<T>

Вибір між винятками та патерном Result<T> залежить від того, чи є помилка очікуваною частиною бізнес-логіки, чи порушенням контракту виконання:

Кидати виняток (Exception) доцільно у справді виняткових ситуаціях, коли метод не може виконати свою роботу через збій інфраструктури або порушення передумов: розрив з'єднання з базою даних, мережевий таймаут, відсутність критичного конфігураційного файлу або передача некоректних аргументів (ArgumentNullException). Винятки автоматично зупиняють подальше виконання невалідного сценарію і зберігають повний стек викликів (StackTrace), але мають високу вартість через розкрутку стека.

Повертати Result<T> (або bool, null, спеціальний об'єкт статусу) доцільно для очікуваних, штатних невдач бізнес-процесу: помилки валідації форми введення, невірний пароль користувача, відсутність запису при пошуку за ID або нестача товару на складі при оформленні замовлення. Це працює значно швидше за винятки, робить можливі помилки явними прямо в сигнатурі методу та позбавляє потреби використовувати дорогі блоки try-catch для керування звичайним потоком програми.

## 4. Загальні висновки

Бібліотека Polly (особливо сучасний конвеєрний API ResiliencePipelineBuilder у Polly v8) дозволяє декларативно відокремити бізнес-логіку від інфраструктурного коду обробки збоїв. Її головні переваги — готові перевірені реалізації патернів (Retry, Circuit Breaker, Timeout, Fallback, Bulkhead), підтримка Exponential Backoff + Jitter, зручне вбудоване логування подій (OnRetry, OnOpened, OnTimeout) та можливість легко комбінувати стратегії в єдиний пайплайн. Серед обмежень і ризиків варто враховувати необхідність коректної підтримки CancellationToken у цільових методах (для роботи Timeout) та обережність при застосуванні Retry до неідемпотентних операцій (наприклад, повторне списання коштів без ключа ідемпотентності).

Поясніть різницю між підходами «кидати виняток» та «повертати Result». Наведіть приклад для кожного.

Виняток (Exception) сигналізує про непередбачуване порушення роботи програми або інфраструктурний збій, перериває поточний потік виконання і розкручує стек викликів до найближчого catch. Приклад: втрата з'єднання з сервером БД (SqlException) або пошкоджений файл конфігурації.

Result<T> явно повертає об'єкт результату (успіх зі значенням або опис очікуваної бізнес-помилки) без витрат на розкрутку стека. Приклад: перевірка коректності email при реєстрації (Result.Failure("Невірний формат email")) або пошук користувача, якого може не бути в базі.

Які три стандартні конструктори рекомендується реалізовувати у власному типі винятку?

Конструктор без параметрів: public MyException() { }

Конструктор із текстовим повідомленням: public MyException(string message) : base(message) { }

Конструктор із повідомленням та внутрішнім винятком (для збереження першопричини при обгортанні винятків): public MyException(string message, Exception innerException) : base(message, innerException) { }

## Контрольні запитання

1. Чим Circuit Breaker відрізняється від Retry? Коли який патерн доцільніший?

Retry повторює виклик у надії, що проблема миттєва і наступна спроба пройде успішно. Доцільний при короткочасних мережевих збоях або тимчасовому блокуванні рядка в БД.

Circuit Breaker припиняє надсилати запити на певний час (Open), якщо сервіс стабільно падає, щоб не витрачати ресурси та дати сервісу відновитися. Доцільний при тривалих збоях зовнішнього сервісу або перевантаженні залежної системи.

2. Для чого потрібен Bulkhead і яку проблему він вирішує?

Bulkhead (Перегородка) обмежує кількість одночасних викликів і виділених потоків/з'єднань для певної операції (ізолює пули ресурсів). Він вирішує проблему каскадного вичерпання ресурсів: якщо один зовнішній API зависне, він вичерпає лише свою виділену квоту потоків, а решта функцій застосунку продовжить стабільно працювати.

3. Чому Jitter важливий при реалізації Retry з експоненційною затримкою?

Якщо тисячі клієнтів одночасно отримають помилку від сервера, без Jitter усі вони чекатимуть однакові інтервали (1с, 2с, 4с) і одночасно завдадуть нового синхронного удару по серверу (ефект Thundering Herd — «тупіт стада»), знову поклавши його. Jitter додає випадкове відхилення до затримки, «розмазуючи» повторні запити в часі.

4. Які ризики виникають при застосуванні Retry до неідемпотентної операції?

Неідемпотентна операція при повторному виконанні змінює стан системи повторно (наприклад, POST /payments без унікального ключа транзакції). Якщо запит насправді виконався на сервері, але відповідь загубилася через мережевий таймаут, Retry відправить запит ще раз, що призведе до подвійного списання коштів, дублювання замовлень або створення кількох однакових записів у БД.
