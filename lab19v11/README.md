# Лабораторна робота No13
• Тема: Власні винятки та патерн Result.
• Тривалість: 80 хв (2 академічні години)
• Інструмент: .NET SDK, IDE на вибір студента

## Мета
Навчитися створювати власні типи винятків для специфічних помилок, а також реалізовувати
патерн Result для більш контрольованої обробки помилок без використання винятків у
“нормальних” сценаріях невдачі.

## Теоретичні відомості
• Власні винятки: Класи, що успадковуються від System.Exception (або його похідних), які
дозволяють створювати специфічні типи помилок для вашого застосунку.

• Патерн Result: Альтернативний підхід до обробки помилок, коли метод повертає об’єкт
Result<T>, який інкапсулює або успішний результат (T), або інформацію про помилку. Це
дозволяє уникнути використання винятків для очікуваних сценаріїв невдачі.

## Хід роботи

У цій лабораторній роботі я створила консольний застосунок для обробки платежів, де реалізувала два різні підходи до обробки помилок залежно від їхньої природи. 
Для критичних технічних збоїв платіжного шлюзу я розробила власний клас винятку PaymentGatewayException із додатковими властивостями (GatewayName та ErrorCode) і 
застосувала його в методі ProcessPayment, обробивши можливі аварії через блок try-catch. Натомість для передбачуваних бізнес-сценаріїв невдачі, 
як-от пошук неіснуючої транзакції під час повернення коштів у методі RefundPayment, я реалізувала узагальнений патерн Result<T> із фабричними методами Success та Failure, 
що дозволило зручно контролювати результат операції через властивості IsSuccess та Error без зайвого навантаження на програму винятками.

## Контрольні запитання
1. Навіщо створювати власні типи винятків? Які переваги це дає?
Власні винятки потрібні для того, щоб описувати специфічні помилки бізнес-логіки або зовнішніх інтеграцій мовою предметної області застосунку, замість використання занадто загальних системних класів (наприклад, Exception чи InvalidOperationException).
Основні переваги:

Семантична зрозумілість: Назва класу (наприклад, PaymentGatewayException) одразу вказує на джерело та суть проблеми без необхідності читати текст повідомлення.

Вибіркове перехоплення: Дозволяє обробляти конкретні помилки в окремих блоках catch і застосовувати для них іншу стратегію відновлення, ніж для системних збоїв.

Передача додаткового контексту: У власний клас можна додати спеціалізовані властивості (наприклад, ErrorCode, GatewayName, TransactionId), які зручно використовувати для логування або формування відповіді користувачу.

2. Які стандартні конструктори рекомендується реалізовувати для власних винятків?
Згідно з офіційними рекомендаціями проєктування .NET, у власному класі винятку варто реалізувати три базові конструктори, які передають параметри базовому класу Exception:

public CustomException() — конструктор за замовчуванням без параметрів.

public CustomException(string message) — приймає текстовий опис причини помилки.

public CustomException(string message, Exception innerException) — приймає опис помилки та посилання на внутрішній виняток (необхідно для обгортання низькорівневих винятків зі збереженням першопричини та стек-трейсу).(Крім них, за потреби додаються кастомні конструктори для ініціалізації власних властивостей класу).

3. Поясніть патерн Result. У яких випадках його використання є більш доцільним, ніж
викидання винятків?
Патерн Result<T> — це підхід до обробки помилок, за якого метод замість викидання винятку повертає об'єкт-контейнер (Result<T>). Цей об'єкт містить прапорець успішності (IsSuccess) та, залежно від результату, або корисні дані (Value), або опис помилки (Error).

Його використання є більш доцільним у таких випадках:

Очікувані помилки: Коли невдача є штатним, прогнозованим варіантом розвитку подій у бізнес-логіці (невірний ввід користувача, сутність не знайдена в базі даних).

Критичність до продуктивності: Механізм винятків у .NET вимагає значних ресурсів на збір та розгортання StackTrace, тоді як повернення об'єкта Result<T> працює як звичайний вихід із методу.

Явність контракту методу: Сигнатура Result<T> змушує розробника явно перевірити успішність виконання операції перед доступом до результату, тоді як винятки не відображаються в сигнатурі методу C#.

4. Які сценарії краще обробляти через винятки, а які через патерн Result?
Через винятки (Exception): Непередбачувані, критичні та інфраструктурні збої, за яких метод не може виконати свій контракт, а подальше виконання поточного сценарію неможливе. Наприклад: втрата з'єднання з базою даних або платіжним шлюзом, відсутність критичного файлу конфігурації, пошкодження даних, помилки мережі чи нестача пам'яті.

Через патерн Result<T>: Передбачувані відмови бізнес-логіки та результати перевірок. Наприклад: помилки валідації форм, пошук неіснуючого запису за ідентифікатором, спроба повернути кошти за вже скасованою транзакцією, недостатньо коштів на рахунку або невірний пароль під час авторизації.
