# Самостійна робота No20

• Тема: Реалізація exponential backoff.
• Обсяг: 80 хв (2 академічні години)

##Мета

Розробити власний допоміжний клас для реалізації патерну Retry з експоненційною затримкою
та випадковим “jitter”.

## Хід роботи

## 1. Опис реалізації `RetryPolicy`

У проєкті `IndependentWork14` реалізовано власний узагальнений клас `RetryPolicy`, який інкапсулює логіку повторного виконання будь-якої операції `Func<T>` при виникненні тимчасових збоїв:
* **Конструктор:** `public RetryPolicy(int maxRetries, TimeSpan initialDelay, double jitterFactor = 0.2)` приймає максимальну кількість повторів, базову затримку та коефіцієнт випадкового відхилення (`jitter`).
* **Формула розрахунку затримки:**
  $$\text{delay} = \text{initialDelay} \times 2^{\text{retryAttempt}} \times (1 + \text{random.NextDouble}() \times \text{jitterFactor} \times 2 - \text{jitterFactor})$$
  Кожна наступна затримка зростає експоненційно ($1\times, 2\times, 4\times, \dots$) із випадковим розкидом $\pm 25\%$.
* **Вибірковість повторів (`shouldRetry`):** опціональний предикат `Func<Exception, bool>` дозволяє повторювати лише тимчасові мережеві збої (`TimeoutException`, `HttpRequestException`) і миттєво припиняти виконання при фатальних помилках (`UnauthorizedAccessException`).

---

## 2. Аналіз результатів демонстрації в `Main`

1. **Сценарій 1 (Успіх після тимчасових збоїв):** Перші дві спроби виклику зовнішнього API завершуються винятком `TimeoutException` (із затримками ~300 мс та ~600 мс з урахуванням jitter), а на 3-й спробі операція успішно повертає курс `41.85 грн`.
2. **Сценарій 2 (Остаточна невдача після вичерпання `maxRetries`):** Сервіс постійно повертає `HttpRequestException (503)`. Політика виконує 1 початкову та 3 повторні спроби (з затримками ~300 мс, ~600 мс, ~1200 мс), після чого прокидає виняток у `Main`.
3. **Сценарій 3 (Фільтрація через `shouldRetry`):** При виникненні `UnauthorizedAccessException` предикат повертає `false`, і політика одразу прокидає помилку без витрати часу на марні повтори.

---

## 3. Висновки щодо меж застосування патерну Retry з exponential backoff

Патерн **Retry з exponential backoff та jitter** є оптимальним для роботи з розподіленими системами, мережевими API, базами даних та брокерами повідомлень при **короткочасних (транзієнтних) збоях** — тимчасовій втраті пакетів, короткому перевантаженні сервісу чи блокуванні рядків у БД. Експоненційне збільшення паузи знижує тиск на проблемний вузол, а *jitter* розсинхронізує потоки клієнтів.

Водночас цей патерн має чіткі межі застосування:
* **Не підходить для тривалих збоїв (Down-стану):** Якщо зовнішній сервіс повністю вийшов з ладу, повторні спроби лише затримують відповідь користувачеві — у таких випадках потрібен патерн *Circuit Breaker*.
* **Небезпечний для неідемпотентних операцій:** Повторне відправлення запиту на створення платежу чи списання коштів без унікального ключа ідемпотентності може призвести до дублювання транзакцій.
* **Безглуздий для логічних помилок і помилок авторизації:** Помилки валідації даних, `NullReferenceException` чи `401 Unauthorized` не зникнуть після очікування, тому їх необхідно виключати через делегат `shouldRetry`.

## Контрольні запитання

1. Які переваги дає LINQ для побудови ETL-пайплайнів порівняно з ручними циклами?
Декларативний стиль: Код описує що саме потрібно зробити з даними (фільтрація, об'єднання, групування, агрегація), а не як керувати індексами, прапорцями та проміжними словниками, що робить бізнес-логіку прозорою.

Відкладене виконання (Deferred Execution): Проміжні оператори (Where, Select, Join) не створюють тимчасові колекції у пам'яті на кожному кроці, а формують єдиний конвеєр ітераторів, який виконується за один прохід під час матеріалізації (.ToList(), .ToArray(), foreach).

Типобезпека на етапі компіляції: На відміну від рядкових SQL-запитів, компілятор перевіряє сумісність типів між усіма етапами трансформації даних до запуску програми.

Легкість модифікації та композиції: Нові умови фільтрації чи правила перетворення легко додаються або виносяться в окремі методи-розширення без переписування структури вкладених циклів.

2. Чому для аналітичних задач часто поєднують Join, GroupBy, Select та OrderBy в одному пайплайні?
Ця послідовність операторів реалізує повний цикл багатовимірної аналітики даних:

Join (Збагачення): Поєднує таблицю фактів (наприклад, продажі) із довідниками (товари, клієнти), підтягуючи необхідні для аналізу атрибути (категорію, ціну, місто).

GroupBy (Сегментація): Розбиває потік об'єднаних записів на логічні групи за обраним виміром (наприклад, за категорією товару чи місяцем).

Select (Агрегація та проєкція): Перетворює кожну групу на підсумковий аналітичний об'єкт за допомогою агрегатних функцій (Sum, Count, Average, Max).

OrderBy / OrderByDescending (Ранжування): Впорядковує розраховані показники для визначення лідерів (топ-N позицій) або побудови хронологічної динаміки.

3. Які фактори можуть найбільше впливати на продуктивність складних LINQ-запитів?
Порядок розташування операторів: Якщо поставити фільтрацію (Where) після Join або GroupBy замість самого початку ланцюжка, система витрачатиме ресурси на об'єднання та групування записів, які згодом усе одно будуть відкинуті.

Багаторазова матеріалізація (Multiple Enumeration): Повторне перебирання запиту типу IEnumerable<T> без попереднього збереження результату через .ToList() змушує весь пайплайн обчислюватися заново при кожному зверненні.

Передчасне сортування: Виклик OrderBy (складність O(NlogN)) до фільтрації та агрегації значно уповільнює обробку великих колекцій.

Надмірні алокації пам'яті: Створення великої кількості проміжних анонімних об'єктів, замикань у лямбда-виразах і викликів .ToList() усередині ланцюжка збільшує навантаження на збирач сміття (GC).

4. Як перевірити, що LINQ-пайплайн не лише працює, а й залишається читабельним і підтримуваним?
Форматування «один оператор — один рядок»: Кожен метод конвеєра (Where, Join, GroupBy, Select) розміщується з нового рядка з однаковим відступом, а параметрам лямбд даються змістовні імена (sale, product, cityGroup) замість однолітерних (x, y).

Декомпозиція надто довгих запитів: Якщо ланцюжок перевищує 10–15 рядків або містить глибоко вкладені підзапити, його розбивають на окремі методи або проміжні змінні з чіткими назвами.

Покриття модульними тестами (Unit Tests): Перевірка роботи пайплайна на невеликих еталонних наборах даних, де результат легко порахувати вручну, із тестуванням граничних випадків (порожні колекції, відсутність збігів при Join, однакові значення при сортуванні).
