## 2. Аналіз прикладів SRP (Single Responsibility Principle)

### 2.1. Вдале застосування SRP (2 приклади)

#### Приклад 1: `OrderService` у проєкті eShopOnWeb
* **Посилання на код:** `https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/ApplicationCore/Services/OrderService.cs` (рядки 18–57, метод `CreateOrderAsync`).
* **Де видно принцип:** Клас `OrderService` відповідає виключно за координацію створення замовлення в бізнес-логіці. Він отримує кошик через `IBasketRepository`, формує позиції замовлення через `IOrderRepository`, і не займається ні прямими SQL-запитами, ні відправкою email-сповіщень, ні логуванням у файл.
* **Переваги для підтримки:** Код читається як чіткий бізнес-сценарій. Будь-які зміни у способі збереження даних у БД не зачіпають цей клас, оскільки робота йде через абстракції репозиторіїв.
* **Що зміниться при додаванні нової функції:** Якщо знадобиться змінити алгоритм розрахунку знижки чи додати перевірку промокоду перед створенням замовлення, змінюватиметься лише бізнес-логіка формування замовлення в цьому сервісі без ризику зламати роботу з базою даних.

#### Приклад 2: `FileDownloader` у проєкті ShareX
* **Посилання на код:** `https://github.com/ShareX/ShareX/blob/develop/ShareX.HelpersLib/FileDownloader.cs` (рядки 35–140).
* **Де видно принцип:** Клас сфокусований на одній конкретній технічній задачі — асинхронному завантаженні файлу за URL із відстеженням прогресу (`ProgressChanged`) та підтримкою скасування (`IsCanceled`). Він не знає, що це за файл (оновлення програми, скриншот чи плагін) і не керує елементами інтерфейсу.
* **Переваги для підтримки:** Клас легко повторно використовувати в різних модулях ShareX (завантаження оновлень, завантаження утиліт FFmpeg тощо). Помилки мережевого потоку локалізовані в одному місці.
* **Що зміниться при додаванні нової функції:** При додаванні завантаження нового типу ресурсів (наприклад, мовних пакетів) клас `FileDownloader` взагалі не доведеться змінювати — достатньо викликати його з іншого місця.

### 2.2. Порушення SRP (2 приклади)

#### Приклад 1: `TaskManager` у проєкті ShareX
* **Посилання на код:** `https://github.com/ShareX/ShareX/blob/develop/ShareX/TaskManager.cs` (рядки 40–350).
* **Де видно порушення:** Клас виступає як "God Object" (Божественний об'єкт). Він одночасно керує чергою завдань, оновлює рядки в таблиці інтерфейсу (`ListView`), веде історію завдань у JSON/XML, керує системним треєм, статистикою завантажень та гарячими клавішами.
* **Ризики для підтримки:** Висока зв'язаність (tight coupling). Зміна структури збереження історії або логіки оновлення UI-таблиці може випадково зламати планування черги виконання завдань. Тестувати такий клас окремо від Windows Forms неможливо.
* **Що зміниться при додаванні нової функції:** При додаванні, наприклад, хмарної синхронізації історії скриншотів доведеться редагувати цей величезний клас, що збільшує ризик регресійних багів в основному процесі захоплення екрана.

#### Приклад 2: `CatalogController` (або `OrderController`) у вебшарі eShopOnWeb
* **Посилання на код:** `https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/Web/Controllers/OrderController.cs` (рядки 24–58).
* **Де видно порушення:** Хоча контролер невеликий, у методі `Detail` він бере на себе одразу кілька ролей: перевірку прав доступу поточного користувача (`User.Identity.Name != viewModel.BuyerId`), виклик MediatR-запиту, перевірку існування об'єкта та формування HTTP-відповідей (`BadRequest`, `View`). У більших контролерах змішування авторизаційних перевірок із маршрутизацією ускладнює код.
* **Ризики для підтримки:** Дублювання перевірок прав власника замовлення в різних методах контролера. Якщо правила доступу ускладняться (наприклад, доступ отримає менеджер магазину), доведеться правити код у кількох екшенах контролера.
* **Що зміниться при додаванні нової функції:** Додавання ролі "Менеджер підтримки", який може переглядати чужі замовлення, вимагатиме втручання в код самого контролера замість зміни політики авторизації.

## 3. Аналіз прикладів розширення за OCP (Open/Closed Principle)

### Приклад 1: Система завантажувачів `ImageUploader` / `FileUploader` у проєкті ShareX
* **Посилання на код:**  
  * Базова абстракція: `https://github.com/ShareX/ShareX/blob/develop/ShareX.UploadersLib/BaseUploaders/ImageUploader.cs` (рядки 30–60, абстрактний метод `Upload(Stream stream, string fileName)`).  
  * Конкретна реалізація (Imgur): `https://github.com/ShareX/ShareX/blob/develop/ShareX.UploadersLib/ImageUploaders/Imgur.cs` (рядки 95–150).
* **Де видно принцип:** Базовий клас `ImageUploader` визначає загальний контракт та допоміжні методи HTTP-запитів, залишаючи конкретну логіку завантаження абстрактною. Кожен сервіс (Imgur, Flickr, Google Drive, Dropbox — понад 80 сервісів) реалізований як окремий клас-спадкоємець.
* **Переваги для підтримки:** Ядро завантаження ShareX закрите для модифікації, але відкрите для розширення. Помилка в API одного сервісу ніяк не впливає на роботу інших.
* **Що зміниться при додаванні нової функції:** Щоб додати підтримку нового фотохостингу, розробнику не потрібно змінювати існуючі класи завантажувачів — достатньо створити новий клас, успадкований від `ImageUploader`, і перевизначити метод `Upload`.

### Приклад 2: Патерн Specification у проєкті eShopOnWeb
* **Посилання на код:**  
  * Базовий клас специфікації: `https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/ApplicationCore/Specifications/CatalogFilterPaginatedSpecification.cs` (рядки 10–25).  
  * Використання в репозиторії: `https://github.com/dotnet-architecture/eShopOnWeb/blob/main/src/Infrastructure/Data/EfRepository.cs`.
* **Де видно принцип:** Замість того, щоб додавати в інтерфейс `IReadRepository<T>` десятки нових методів (`GetProductsByBrand`, `GetProductsByTypeAndPrice` тощо), використовується патерн **Specification**. Репозиторій приймає абстрактну специфікацію (`ISpecification<T>`), а конкретні критерії фільтрації виносяться в окремі класи-специфікації.
* **Переваги для підтримки:** Інтерфейс та реалізація репозиторію залишаються незмінними (закритими для модифікації) протягом усього життєвого циклу проєкту.
* **Що зміниться при додаванні нової функції:** При додаванні фільтрації товарів за рейтингом або наявністю на складі створюється лише новий клас специфікації (наприклад, `CatalogInStockSpecification`), без редагування самого репозиторію.

## 4. Пропозиція рефакторингу для найгіршого прикладу

**Обраний приклад:** Клас `TaskManager` із проєкту **ShareX** (`ShareX/TaskManager.cs`), який порушує SRP, поєднуючи бізнес-логіку керування чергою завдань, роботу з UI (`ListView`) та збереження історії.

### Суть рефакторингу:
Розділити монолітний `TaskManager` на 3 окремі класи за зонами відповідальності та зв'язати їх через події або інтерфейси:
1. **`TaskQueueService`** — відповідає виключно за життєвий цикл завдань (додавання в чергу, запуск паралельних потоків завантаження, зупинка) та генерує події (`TaskAdded`, `TaskStatusChanged`, `TaskCompleted`).
2. **`TaskHistoryRepository` (реалізація `ITaskHistoryRepository`)** — відповідає лише за серіалізацію та збереження завершених завдань у файл історії (`History.json`).
3. **`TaskListViewPresenter`** — підписується на події `TaskQueueService` і відповідає виключно за візуальне оновлення рядків у компоненті `ListView` на формі.

### Приклад структури після рефакторингу (C#):
```csharp
public interface ITaskHistoryRepository
{
    void SaveTask(TaskInfo taskInfo);
}

public class TaskQueueService
{
    private readonly ITaskHistoryRepository _historyRepository;
    public event Action<WorkerTask>? TaskStatusChanged;

    public TaskQueueService(ITaskHistoryRepository historyRepository)
    {
        _historyRepository = historyRepository;
    }

    public void StartTask(WorkerTask task)
    {
        // Логіка запуску завдання без прив'язки до UI
        task.StatusChanged += () => TaskStatusChanged?.Invoke(task);
        task.Completed += () => _historyRepository.SaveTask(task.Info);
        task.Start();
    }
}


### Контрольні запитання 

**1. Як відрізнити окрему відповідальність класу від просто великого обсягу коду?**
Критерій SRP визначається не кількістю рядків коду, а **кількістю причин для зміни класу** (або кількістю різних бізнес-акторів, яким цей клас підпорядковується).
* Клас може мати 300 рядків коду (наприклад, складний математичний парсер або алгоритм розрахунку податків), але мати **одну відповідальність** — усі ці рядки зміняться лише тоді, коли зміниться формула розрахунку.
* Клас на 60 рядків порушує SRP, якщо він одночасно розраховує суму замовлення, зберігає його в БД і відправляє лист клієнту — у нього є **три різні причини для зміни** (бізнес-правила, схема БД, шаблон листа).

**2. Які ознаки в коді найкраще підтверджують дотримання OCP?**
* **Використання абстракцій у точках варіативності:** Класи взаємодіють через інтерфейси (`IPaymentProcessor`, `ISpecification<T>`) або абстрактні базові класи (`ImageUploader`), а не через жорстко прописані конкретні реалізації.
* **Відсутність великих конструкцій `if / else` або `switch` за типом об'єкта:** Нова поведінка додається створенням нового класу (реалізації інтерфейсу чи спадкоємця), а не дописуванням нової гілки `case` в існуючому методі.
* **Використання патернів проєктування:** Наявність патернів Стратегія (Strategy), Декоратор (Decorator), Специфікація (Specification), Плагінна архітектура або Dependency Injection (DI-контейнер реєструє реалізації без зміни клієнтського коду).

**3. Чому для аналізу SRP/OCP важливо дивитися не лише на інтерфейси, а й на місця розширення системи?**
Наявність інтерфейсу сама по собі ще не гарантує дотримання OCP. Наприклад, якщо в проєкті є інтерфейс `IUploader` і 10 його реалізацій, але десь у головному класі стоїть фабричний метод із величезним `switch (uploaderType) { case "Imgur": return new Imgur(); ... }`, то при додаванні нового завантажувача все одно доведеться **модифікувати існуючий код** у місці виклику. Тому важливо перевіряти саме точки інтеграції/розширення (DI-реєстрацію, плагіни, обробники подій), щоб переконатися, що новий функціонал підключається без переписування ядра системи.

**4. Які ризики виникають, якщо застосовувати рефакторинг “під патерн” без реальної потреби?**
Це явище називається **передчасною абстракцією (Over-engineering)** і несе такі ризики:
* **Ускладнення читання та навігації (Code Fragmentation):** Замість одного зрозумілого класу на 50 рядків з'являється 10 файлів з інтерфейсами, фабриками та адаптерами, через що важко простежити потік виконання програми.
* **Неправильні абстракції:** Якщо створити абстракцію до того, як з'являться реальні вимоги до розширення, вона може виявитися невідповідною майбутнім сценаріям, і її доведеться повністю переписувати (що дорожче, ніж рефакторинг простого коду).
* **Збільшення часу розробки:** Витрачається час на підтримку зайвого шаблонного коду (boilerplate) для сценаріїв розширення, які на практиці ніколи не знадобляться (порушення принципу YAGNI — *You Aren't Gonna Need It*).
