# Звіт з самостійної роботи №9
**Тема:** Делегати й лямбда-вирази: власні утиліти для колекцій.

## 1. Завдання та реалізація
В рамках роботи було створено статичний узагальнений клас `CollectionUtils`, який містить чотири методи-утиліти для маніпуляції колекціями за допомогою делегатів:
- `Map<TSource, TResult>` — приймає `Func<TSource, TResult>` для трансформації кожного елемента.
- `MaxBy<T, TKey>` — приймає `Func<T, TKey>` для пошуку елемента з максимальним значенням ключа.
- `Filter<T>` — приймає `Predicate<T>` для відбору елементів за умовою.
- `ForEach<T>` — приймає `Action<T>` для виконання дії над кожним елементом.

---

## 2. Відповіді на питання звіту

### Навіщо потрібні делегати для створення таких утиліт?
Делегати дозволяють відокремити алгоритм обходу колекції від конкретної логіки обробки даних. Вони передають поведінку (функцію/метод) як параметр у метод, роблячи утиліти повністю універсальними та придатними для повторного використання з будь-якими типами даних та умовами.

### Як лямбда-вирази спрощують виклик цих методів?
Лямбда-вирази (`p => p.Price > 1000`) дозволяють записувати анонімну функцію безпосередньо у місці виклику методу, уникаючи необхідності оголошувати окремі іменовані класи чи методи. Це робить код значно коротшим, виразнішим та легшим для читання.

### Порівняння власних методів із вбудованими LINQ-операторами
- `Map` є аналогом LINQ-оператора `Select`.
- `Filter` є аналогом LINQ-оператора `Where`.
- `MaxBy` відповідає LINQ-методу `MaxBy` (включеному в .NET 6+).
- `ForEach` аналогічний методу `List<T>.ForEach`.

*Основна відмінність:* Наші власні методи виконуються негайно (Eager Evaluation) і повертають нові списки `List<T>`, тоді як більшість операторів LINQ використовують відкладене виконання (Deferred Execution) через `yield return`.

## Хід роботи

У цій самостійній роботі я створила консольний проєкт lab9-self-v1 та реалізувала статичний узагальнений клас CollectionUtils із чотирма методами-утилітами (Map, MaxBy, Filter, ForEach), які приймають делегати Func, Predicate та Action. Роботу методів було продемонстровано у Program.cs на трьох різних типах колекцій (List<Product>, List<int>, List<string>) з використанням лямбда-виразів, а також складено аналітичний звіт у файлі README.md із порівнянням власних утиліт із LINQ та завантажено проєкт на GitHub.

## Контрольні запитання (просто текстом)

1.Чому делегати є зручним механізмом для передавання поведінки в узагальнені методи?

Делегати діють як покажчики на методи з визначеною сигнатурою, що дозволяє передавати функціональність або обчислювальну логіку безпосередньо у вигляді параметрів методу. Завдяки цьому узагальнений метод контролює лише процес обходу та структуризації колекції, а конкретні правила фільтрації, трансформації чи обробки залишаються на розсуд викликаючого коду.

2.У чому різниця між Func<T, TResult>, Action<T> та Predicate<T>?

Func<T, TResult> — це делегат, який приймає один або кілька аргументів і обов'язково повертає значення вказаного типу TResult. Action<T> — це делегат для виконання дій, який приймає аргументи, але нічого не повертає (тип повернення void). Predicate<T> — це спеціалізований делегат для перевірки умов, який приймає один аргумент типу T і завжди повертає логічне значення bool.

3.Які переваги дає поєднання generic-методів і лямбда-виразів під час роботи з колекціями?

Поєднання дженериків та лямбда-виразів забезпечує високу гнучкість, повторне використання коду та строгу типобезпеку без втрати швидкодії. Дженерики дозволяють писати універсальний алгоритм для будь-яких типів даних, а лямбда-вирази дозволяють лаконічно описувати необхідні правила обробки безпосередньо у місці виклику методу без створення зайвих класичних функцій.

4.У яких випадках власні утиліти на кшталт Map чи Filter корисно реалізувати самостійно, навіть якщо існує LINQ?

Власні утиліти корисно реалізовувати для кращого розуміння внутрішнього влаштування функціонального програмування у C#, а також у специфічних сценаріях, коли потрібно уникнути накладних витрат відкладеного виконання LINQ (Deferred Execution), створити оптимізований алгоритм обходу без зайвих аллокацій пам'яті в закритих системних модулях або коли розробка ведеться під середовища з обмеженнями на стандартні бібліотеки.
