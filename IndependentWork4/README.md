# Cамостійної роботи №4
**Тема:** Розширення ієрархії та наслідки змін базового класу.

## 1. Аналіз наслідків модифікації базового класу `LibraryItem`
При додаванні нового поля `_uniqueId` та відповідного параметра до конструктора базового класу `LibraryItem`:
- **Необхідні зміни в похідних класах (`Book`, `Journal`):** Усі конструктори похідних класів мусили бути модифіковані для прийняття нового параметра `uniqueId` і явного передавання його в базовий конструктор за допомогою виклику `: base(uniqueId, ...)`.
- **Причина виникнення проблем:** Оскільки в `LibraryItem` був відсутній конструктор за замовчуванням (без параметрів), C# вимагає, щоб кожен похідний клас обов'язково викликав доступний конструктор базового класу та передавав у нього всі необхідні для ініціалізації параметри. Зміна сигнатури базового конструктора призводить до виклику «хвильового ефекту» (ripple effect) по всій ієрархії наслідування.

## 2. Переваги та недоліки наслідування
- **Переваги:**
  - **Повторне використання коду (Code Reuse):** Базові поля (`Title`, `PublicationYear`, `UniqueId`) та методи оголошуються лише один раз у базовому класі.
  - **Поліморфізм:** Об'єкти `Book`, `Journal` та `AudioBook` можна обробляти однотипно через посилання на базовий тип `LibraryItem`.
  - **Легке розширення:** Клас `AudioBook` легко розширив `Book`, додавши лише одне поле `_narrator` та перевизначивши метод `DisplayDetails()`.

- **Недоліки:**
  - **Жорстка зв'язаність (Fragile Base Class Problem):** Зміна сигнатури конструктора або поведінки базового класу може зламати компіляцію чи розірвати логіку всіх похідних класів.
  - **Каскадні зміни:** Зміна в `LibraryItem` вимагала редагування не лише прямих нащадків (`Book`, `Journal`), а й «онуків» (`AudioBook`).

- **Коли наслідування доцільне:**
  - Коли між сутностями існує чітке відношення **"IS-A"** (Аудіокнига Є Книгою, Книга Є Бібліотечним елементом).
  - Коли ієрархія є стабільною і базові класи не піддаються частим змінам у сигнатурах конструкторів.

##  Контрольні запитання

1.Як зміна конструктора базового класу вплинула на похідні класи?

Зміна сигнатури конструктора базового класу LibraryItem (додавання обов'язкового параметра uniqueId) призвела до втрати здатності похідних класів Book та Journal компілюватися без оновлення коду. Оскільки базовий клас не мав конструктора за замовчуванням, усі похідні класи мусили модифікувати власні конструктори, щоб приймати новий параметр і явно передавати його в базовий конструктор через виклик : base(uniqueId, ...).

2.Чим відрізняється розширення ієрархії через новий похідний клас від модифікації наявного базового класу?

Розширення ієрархії через створення нового похідного класу (наприклад, AudioBook) дотримується принципу відкритості/закритості (SOLID): воно додає нову функціональність, не порушуючи існуючий код і не вимагаючи внесення змін до інших класів. Натомість модифікація наявного базового класу викликає каскадні зміни по всій ієрархії наслідування, змушуючи переписувати або доопрацьовувати всі існуючі похідні класи.

3.У яких випадках для цієї задачі композиція могла б бути кращою за наслідування?

Композиція була б кращою, якби один об'єкт міг змінювати свої ролі чи формати під час виконання програми — наприклад, якби паперова книга одночасно мала електронну чи аудіоверсію. Замість створення окремого класу AudioBook (через наслідування), клас Book міг би мати поле-компонент AudioTrack, що дозволило б уникнути "проблеми крихкого базового класу" та робило б систему гнучкішою при додаванні нових форматів носіїв.

4.Як поліморфний виклик DisplayDetails() допомагає перевірити правильність ієрархії?

Виклик перевизначеного методу DisplayDetails() дозволяє перевірити, чи правильно налаштовано механізм наслідування та перевизначення (virtual/override). Це гарантує, що при зверненні до об'єкта викликається саме його власна реалізація методу з розширеним набором полів (автор, номер випуску, диктор), а також підтверджує, що базовий стан об'єкта було коректно ініціалізовано через ланцюжок викликів base(...).
