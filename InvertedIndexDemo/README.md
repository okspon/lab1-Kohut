# Самостійна робота №10

**Тема:** Інвертований індекс та вимірювання продуктивності.

## Хід роботи
У цій самостійній роботі я створила консольний проєкт InvertedIndexDemo, у якому реалізувала структуру даних інвертованого індексу на базі Dictionary<string, HashSet<int>> та токенізацію тексту із вилученням стоп-слів у класі TextProcessor. Також було реалізовано методи мультипошуку за логічними операціями AND (IntersectWith) та OR (UnionWith), проведено вимірювання продуктивності порівняно з лінійним пошуком для 10, 100, 1000 та 10000 документів (де індекс показав прискорення у тисячі разів), складено аналітичний звіт у файлі REPORT.md та успішно відправлено всі файли на GitHub.

## Контрольні запитання 

1.Чому структура Dictionary<string, HashSet<int>> добре підходить для реалізації інвертованого індексу?

Словник Dictionary<string, HashSet<int>> дозволяє миттєво знайти список ідентифікаторів документів за терміном (словом) за константний час 
O(1). Використання HashSet<int> як значення запобігає дублюванню ID одного й того самого документа в межах одного слова та дає змогу проводити ефективні множинні операції перетину та об'єднання.

2.Які переваги HashSet<T> дає під час обчислення AND/OR-пошуку за кількома словами?

HashSet<T> містить оптимізовані вбудовані методи IntersectWith (для реалізації логічного "AND") та UnionWith (для реалізації логічного "OR"). Ці операції виконуються за час 
O(N) від кількості елементів у множині без створення додаткових масивів та без потреби в ручному переборі циклом.

3.Чому під час вимірювання продуктивності важливо однаково нормалізувати текст для лінійного пошуку та пошуку через індекс?

Однакова нормалізація (нижній регістр, прибрання пунктуації та стоп-слів) гарантує порівнянність і точність алгоритмів. Якщо нормалізація буде різною, лінійний пошук та пошук за індексом повернуть різну кількість знайдених документів, що зробить порівняння часу виконання методично некоректним та викривить результати бенчмарку.

4.Які обмеження має проста реалізація інвертованого індексу без ранжування, стемінгу та підтримки фраз?

Проста реалізація не враховує релевантність результатів (всі знайдені документи виводяться в довільному порядку без оцінки TF-IDF), не знаходить словоформи одного слова (наприклад, "program" і "programming" сприймаються як абсолютно різні слова без стемінгу) та не здата шукати точні фрази з урахуванням порядку слів у тексті.
