# Звіт до самостійної роботи №16
**Тема:** Колекції в практиці ООП: інвертований індекс і вимірювання продуктивності

---

## 1. Опис реалізації
У проєкті `InvertedIndexDemo` реалізовано систему повнотекстового пошуку на базі інвертованого індексу:
* **`Document`** — модель документа з полями `Id`, `Title` та `Content`.
* **`TextProcessor`** — утилітарний клас для нормалізації тексту: переведення у нижній регістр (`ToLowerInvariant`), вилучення токенів за допомогою регулярного виразу `[a-zа-яіїєґ0-9#]+` (що зберігає специфічні терміни на кшталт `c#`) та фільтрації стоп-слів (`a`, `an`, `the`, `is`, `are` тощо) за допомогою `HashSet<string>`.
* **`InvertedIndex`** — індекс на базі `Dictionary<string, HashSet<int>>` (відображення слова у множину ID документів) та `Dictionary<int, Document>` (для отримання об'єкта документа за ID зі складністю $O(1)$). Реалізовано три типи пошуку:
  * `SearchSingleWord` — пошук за одним словом за $O(1)$.
  * `SearchMultipleWords` (логічне `AND`) — послідовний перетин множин ID документів через `HashSet<int>.IntersectWith`.
  * `SearchAnyWord` (логічне `OR`) — об'єднання множин ID документів через `HashSet<int>.UnionWith`.

## 3. Висновки та аналіз порогу вигідності індексу

1. **Асимптотична складність:**
   * **Лінійний пошук** має складність **$O(N \cdot M)$**, де $N$ — кількість документів, а $M$ — середня довжина документа (оскільки кожного разу доводиться токенізувати та перевіряти текст кожного документа). Час пошуку зростає лінійно пропорційно до кількості документів.
   * **Пошук через Inverted Index** має складність **$O(1)$** для знаходження множини ID документів за словом у `Dictionary` та **$O(K)$** для матеріалізації списку результатів (де $K$ — кількість знайдених збігів).
2. **Поріг вигідності індексу (Break-even point):**
   * Побудова індексу потребує одноразових витрат часу ($O(N \cdot M)$) та додаткової оперативної пам'яті.
   * Якщо потрібно виконати **лише 1 пошуковий запит** по невеликій колекції (до 10–50 документів), лінійний пошук вигідніший сумарно, оскільки не витрачається час на індексацію.
   * Проте вже починаючи з **100+ документів** або при виконанні **навіть 2–3 пошукових запитів** підряд по тій самій базі, інвертований індекс повністю окупає витрати на побудову і працює в **сотні разів швидше** за лінійний перебір.
