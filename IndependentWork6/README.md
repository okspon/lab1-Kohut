# Самостійна робота №6
**Тема:** Інтерфейс vs абстрактний клас — практичні критерії.

## Сценарій 1: Система сповіщень
### Обраний підхід: Інтерфейс `INotifier`
### Обґрунтування вибору:
1. **Відсутність спільного стану/коду:** Канали сповіщень (Email, SMS, Push) істотно відрізняються за своєю реалізацією та технологіями. Вони не мають спільної логіки, яку доцільно виносити в базовий клас.
2. **Множинне наслідування:** Класи сповіщень можуть реалізовувати декілька контрактів одночасно (наприклад, `INotifier`, `ILogger`, `IDisposable`). Оскільки C# не підтримує множинне наслідування класів, використання інтерфейсу залишає клас гнучким.
3. **Слабке зв'язування:** Клієнтський код взаємодіє виключно з контрактом `INotifier`, що спрощує додавання нових типів сповіщень без зміни існуючої системи.


## Сценарій 2: Обробка файлів
### Обраний підхід: Абстрактний клас `FileProcessor`
### Обґрунтування вибору:
1. **Повторне використання коду:** Усі обробники файлів мають спільну логіку (відкриття та закриття файлу, збереження шляху до файлу). Реалізація цих кроків в абстрактному класі запобігає дублюванню коду.
2. **Шаблонний метод (Template Method):** Абстрактний клас реалізує спільний алгоритм `Process()`, викликаючи спільні методи `OpenFile()`, `CloseFile()` та абстрактний метод `ProcessContent()`. Похідні класи реалізують лише специфічну логіку обробки вмісту.
3. **Тісна родинна зв'язаність (IS-A):** Усі обробники є конкретними різновидами процесора файлів, тому наслідування від спільної абстрактної сутності повністю виправдане.

---

## Загальні висновки:
- **Інтерфейси** слід обирати, коли необхідно задати лише контракт поведінки ("CAN-DO") для непов'язаних між собою класів, або коли потрібна підтримка реалізації кількох контрактів одним класом.
- **Абстрактні класи** варто використовувати, коли класи мають чітке відношення "IS-A", мають спільну базову логіку/стан (поля, готові методи) та потребують контролю над загальним алгоритмом виконання.

## Контрольні запитання

1.Які ознаки підказують, що сценарій краще моделювати через інтерфейс?

Якщо класи є різнотипними і не мають спільного базового стану або готового коду для повторного використання, а лише мають виконувати однакову дію (контракт поведінки "CAN-DO"), або коли клас уже успадковується від іншого класу і йому потрібна можливість реалізувати додаткову поведінку, найкраще підходить інтерфейс.

2.У чому перевага абстрактного класу для процесів зі спільними кроками виконання?

Абстрактний клас дозволяє реалізувати спільні кроки алгоритму один раз у базовому класі (наприклад, через паттерн "Шаблонний метод"), що позбавляє дублювання коду в похідних класах та забезпечує єдиний порядок виконання процесів.

3.Як порівняння двох підходів допомагає прийняти архітектурне рішення?

Зіставлення вимог до наявності спільного стану/коду (абстрактний клас) та потреби у гнучкому множинному контракті (інтерфейс) дозволяє уникнути двох крайнощів: створення жорстких ієрархій наслідування з "крихкими базовими класами" або дублювання однакової логіки в багатьох реалізаціях інтерфейсу.

4.Яку роль у ваших прикладах відіграє поліморфізм?

Поліморфізм дозволяє обробляти об'єкти за допомогою єдиного базового типу (колекції List<INotifier> або List<FileProcessor>), викликаючи спільні методи (Send або Process) без знання про те, який саме конкретний клас розробляв цей функціонал, запевняючи виконання потрібної логіки для кожного окремого випадку.
