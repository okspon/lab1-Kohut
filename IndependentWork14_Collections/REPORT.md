# Звіт до самостійної роботи №14
**Тема:** Вивчення `Dictionary<TKey, TValue>` та `HashSet<T>` у бібліотеках .NET

---

## 1. Результати аналізу використання у відкритих проєктах (.NET Open-Source)

### Приклад 1: `Dictionary<TKey, TValue>` у Newtonsoft.Json (`DefaultContractResolver`)
* **Джерело:** `Newtonsoft.Json` (`Src/Newtonsoft.Json/Serialization/DefaultContractResolver.cs` — кеш контрактів серіалізації `_instanceContractCache`).
* **Контекст:** Під час серіалізації/десеріалізації JSON бібліотека аналізує властивості C#-класів через рефлексію (`Reflection`), що є дорогою операцією. Щоб не виконувати аналіз повторно для одного й того самого типу `Type`, результати зберігаються у словнику.
* **Чому обрано `Dictionary<TKey, TValue>`:** Потрібне миттєве зіставлення «ключ (`ResolverContractKey` / `Type`) $\rightarrow$ значення (`JsonContract`)». Використання `List` вимагало б лінійного перебору $O(n)$ при кожній серіалізації об'єкта.
* **Складність операцій:** Пошук (`TryGetValue`) та додавання — **$O(1)$** у середньому випадку.
* **Особливі вимоги:** Реалізовано власний тип ключа `ResolverContractKey` із перевизначеними методами `Equals` та `GetHashCode` для коректного обчислення хешу пари `(Type resolverType, Type contractType)`.

### Приклад 2: `HashSet<T>` у Entity Framework Core (`ModelValidator` / `ChangeTracker`)
* **Джерело:** `dotnet/efcore` (`src/EFCore/Infrastructure/ModelValidator.cs` — перевірка циклічних залежностей і вже відвіданих сутностей).
* **Контекст:** Під час валідації графа моделей сутностей та навігаційних властивостей EF Core обходить зв'язки між таблицями й повинен відстежувати вже перевірені вузли, щоб уникнути дублювання перевірок та нескінченної рекурсії.
* **Чому обрано `HashSet<T>`:** Потрібна лише перевірка унікальності й належності елемента до множини (`visited.Add(entityType)` / `visited.Contains(entityType)`) без збереження додаткового значення-супутника.
* **Складність операцій:** Додавання (`Add`) та перевірка наявності (`Contains`) — **$O(1)$** у середньому випадку (проти $O(n)$ у `List<T>.Contains`).
* **Особливі вимоги:** Для порівняння посилань або метаданих використовується `ReferenceEqualityComparer` або спеціалізований `IEqualityComparer<T>`.

### Приклад 3 (комбінований): `Dictionary<TKey, HashSet<T>>` у Dapper (`SqlMapper` / кешування метаданих запитів)
* **Джерело:** `DapperLib/Dapper` (`Dapper/SqlMapper.cs`).
* **Контекст:** Для прив'язки параметрів SQL-запитів та відстеження унікальних імен параметрів для кожного шаблону запиту використовується комбінація хеш-таблиці ключів та множини унікальних значень.
* **Складність:** Доступ до групи за ключем — $O(1)$, перевірка унікальності елемента в групі — $O(1)$.

## 2. Порівняльна таблиця складності операцій

| Операція | `List<T>` | `Dictionary<TKey, TValue>` | `HashSet<T>` |
| :--- | :--- | :--- | :--- |
| **Коли використовувати** | Впорядковані послідовності, доступ за індексом, дозволені дублікати | Швидкий пошук і оновлення даних за унікальним ключем (кеші, індекси) | Зберігання унікальних елементів, швидка перевірка належності та операції над множинами |
| **Додавання** | $O(1)$ амортизоване ($O(n)$ при розширенні масиву) | $O(1)$ у середньому ($O(n)$ при колізіях/рехешуванні) | $O(1)$ у середньому ($O(n)$ при колізіях/рехешуванні) |
| **Пошук за значенням** | $O(n)$ | $O(n)$ (`ContainsValue`) | $O(1)$ у середньому |
| **Пошук за ключем** | N/A | $O(1)$ у середньому | N/A |
| **Видалення** | $O(n)$ (через зсув елементів) | $O(1)$ у середньому | $O(1)$ у середньому |
| **Перевірка наявності** | $O(n)$ (`Contains`) | $O(1)$ (`ContainsKey`) | $O(1)$ (`Contains`) |

## 3. Висновки про вибір колекції

* **Коли `Dictionary<TKey, TValue>` краще за `List<T>`:** Коли дані мають унікальний ідентифікатор (шлях до файлу, ID користувача, слово-токен) і головною операцією є миттєвий пошук, оновлення або перевірка існування запису за цим ключем. На 100 000 елементів `Dictionary` знаходить запис за ~1 крок ($O(1)$), тоді як `List` у середньому перебирає 50 000 елементів ($O(n)$).
* **Коли `HashSet<T>` є оптимальним вибором:** Коли потрібно гарантувати відсутність дублікатів (наприклад, теги статті, унікальні IP-адреси, ID документів) або виконувати теоретико-множинні операції: об'єднання (`UnionWith`), перетин (`IntersectWith`) чи різницю (`ExceptWith`).
* **Підводні камені при використанні:**
  1. **Зміна полів ключа після додавання:** Якщо використати як ключ змінний об'єкт (`mutable class`), від якого залежить `GetHashCode()`, і змінити його поле після додавання у `Dictionary` або `HashSet`, елемент стане неможливо знайти чи видалити.
  2. **Відсутність гарантованого порядку:** Елементи в `HashSet` та `Dictionary` не призначені для доступу за індексом (`set[0]` не існує).
  3. **Врахування регістру рядків:** За замовчуванням `"C#"` і `"c#"` вважаються різними ключами — для текстових ідентифікаторів слід явно передавати `StringComparer.OrdinalIgnoreCase`.
