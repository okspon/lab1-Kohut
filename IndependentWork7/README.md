# Самостійна робота №7
**Тема:** Узагальнений кеш `Cache<TKey, TValue>` із тестами.

## 1. Опис реалізації
У проєкті реалізовано узагальнений клас `Cache<TKey, TValue>` з політикою витіснення елементів FIFO (First In, First Out).
- Для забезпечення миттєвого пошуку значень за O(1) використано `Dictionary<TKey, TValue>`.
- Для відстеження порядку додавання елементів використано чергу `Queue<TKey>`.
- При перевищенні ємності `_capacity` найстаріший ключ видаляється з черги командою `Dequeue()` і вилучається зі словника.

## 2. Результати тестування
У проєкті `IndependentWork7.Tests` реалізовано юніт-тести xUnit, що перевіряють:
- Додавання та отримання елементів.
- Перевірку наявності ключа (`ContainsKey`).
- Викидання `KeyNotFoundException` при відсутності ключа.
- Видалення найстарішого елемента при переповненні кешу (політика FIFO).

## 3. Відповіді на контрольні запитання

1. **Які переваги надає `Cache<TKey, TValue>` порівняно з окремими неузагальненими реалізаціями кешу?**  
Узагальнений кеш `Cache<TKey, TValue>` забезпечує строгу типобезпеку (Type Safety) на етапі компіляції, що запобігає помилкам приведення типів під час виконання програми. Окрім цього, використання дженериків уникає зайвих операцій пакування та розпакування (boxing/unboxing) при роботі зі значущими типами даних (Value Types), що підвищує продуктивність і дозволяє повторно використовувати один і той самий клас кешу для будь-яких комбінацій типів ключів і значень без створення окремих класів під кожен тип.

2. **Чому для реалізації політики FIFO зручно поєднувати `Dictionary<TKey, TValue>` з `Queue<TKey>` або `LinkedList<TKey>`?**  
Таке поєднання дозволяє досягти оптимальної швидкодії для двох головних операцій. Словник `Dictionary<TKey, TValue>` забезпечує миттєвий пошук, отримання та додавання значень за ключем за константний час O(1). Водночас черга `Queue<TKey>` або зв'язаний список `LinkedList<TKey>` ефективно відстежує хронологічний порядок додавання елементів. Коли кеш переповнюється, черга дозволяє за O(1) визначити та вилучити найстаріший ключ (`Dequeue`), який потім відразу видаляється зі словника.

3. **У яких випадках метод `Get` повинен викидати `KeyNotFoundException`, а коли доцільніше використовувати підхід на кшталт `TryGetValue`?**  
Метод `Get` повинен викидати `KeyNotFoundException`, коли за логікою програми запитуваний ключ обов'язково має бути присутнім у кеші, і його відсутність вважається винятковою ситуацією або помилкою викликаючого коду. Натомість підхід `TryGetValue` доцільніше використовувати для повсякденної перевірки наявності даних у кеші, оскільки він повертає `bool` та не створює накладних витрат на генерування та обробку винятків у нормальному сценарії роботи програми (Cache Miss).

4. **Які тести є критично важливими для перевірки політики витіснення елементів з кешу?**  
Критично важливими є тести на перевищення ємності (Overflow/Eviction Test), які додають кількість елементів, що перевищує задану `_capacity`, і перевіряють, що з кешу вилучився саме найстаріший елемент (перший доданий), а останні додані елементи залишилися доступними. Також важливі тести на коректність зміни властивості `Count` після витіснення (значення має залишатися рівним `_capacity`) та тести, що підтверджують викидання `KeyNotFoundException` при спробі звернутися до вже витісненого ключа.
