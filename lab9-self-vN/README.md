# Самостійна робота No15
• Тема: Делегати й лямбда-вирази: власні утиліти для колекцій.
• Обсяг: 80 хв (2 академічні години)

## Мета

Поглибити розуміння делегатів та лямбда-виразів через створення власних узагальнених методів-
утиліт для роботи з колекціями та повторного використання логіки.#, а також у специфічних сценаріях, коли потрібно уникнути накладних витрат відкладеного виконання LINQ (Deferred Execution), створити оптимізований алгоритм обходу без зайвих аллокацій пам'яті в закритих системних модулях або коли розробка ведеться під середовища з обмеженнями на стандартні бібліотеки.

## Хід роботи
У межах цієї роботи я створила консольний проєкт lab9-self-vN та реалізувала статичний клас CollectionUtils із чотирма узагальненими методами-утилітами для обробки колекцій: Map<TSource, TResult>, MaxBy<T, TKey>, Filter<T> та ForEach<T> із використанням стандартних делегатів Func, Predicate та Action. Я продемонструвала роботу всіх методів на трьох різних типах колекцій (List<Product>, List<int> та List<string>) за допомогою різноманітних лямбда-виразів, порівняла власні утиліти з вбудованими операторами LINQ у звіті та завантажила готовий проєкт у репозиторій на GitHub.

## Контрольні запитання
1. Чому делегати є зручним механізмом для передавання поведінки в узагальнені методи?
Делегати в C# виступають як типізовані посилання на методи (об'єктно-орієнтований аналог вказівників на функції), що дозволяє передавати алгоритми як звичайні параметри. У поєднанні з узагальненими методами це дає такі переваги:

Відокремлення обходу від бізнес-логіки: Узагальнений метод бере на себе механіку проходження по колекції (foreach), перевірку меж або створення нової колекції, а делегат визначає лише унікальну дію над конкретним елементом (умову фільтрації, правило трансформації тощо).

Відсутність зайвих абстракцій: Без делегатів для кожної нової умови довелося б створювати окремий інтерфейс (наприклад, IFilter<T>) та реалізовувати його в новому класі (патерн «Стратегія»). Делегат дозволяє передати метод напряму без створення допоміжних класів.

Повна безпека типів (Type Safety): Компілятор перевіряє відповідність типів параметрів та повертаного значення делегата ще на етапі компіляції.

2. У чому різниця між Func<T, TResult>, Action<T> та Predicate<T>?
Усі три типи є стандартними вбудованими узагальненими делегатами .NET, але вони відрізняються сигнатурою (тим, що приймають і що повертають):

Func<T, TResult> — делегат, який приймає вхідний параметр типу T (існує перевантаження до 16 вхідних параметрів) і обов'язково повертає результат типу TResult. Використовується для перетворень даних або вибору ключів (наприклад, у Map<TSource, TResult> або MaxBy<T, TKey>).

Action<T> — делегат, який приймає параметр типу T (також від 0 до 16 параметрів), але нічого не повертає (void). Використовується для виконання побічних дій: виводу в консоль, запису у файл, зміни стану об'єкта (наприклад, у методі ForEach<T>).

Predicate<T> — спеціалізований делегат, який приймає один параметр типу T і завжди повертає bool (true або false). За своєю суттю він є еквівалентом Func<T, bool>, але семантично підкреслює, що метод виконує перевірку певної умови чи критерію (наприклад, у Filter<T> або List<T>.Find).

3. Які переваги дає поєднання generic-методів і лямбда-виразів під час роботи з колекціями?
Універсальність та повторне використання коду (DRY): Generic-методи дозволяють написати алгоритм один раз для будь-яких типів (int, string, Product), уникаючи дублювання коду та витрат на boxing/unboxing.

Максимальна стислість та читабельність: Лямбда-вирази дозволяють описувати логіку обробки безпосередньо в місці виклику методу в один рядок (CollectionUtils.Filter(products, p => p.Price > 1000)), замість оголошення окремих іменованих методів у класі.

Автоматичне виведення типів (Type Inference): Компілятор самостійно визначає типи параметрів лямбда-виразу на основі типу колекції, переданої в generic-метод, тому розробнику не потрібно писати зайві вказівки типів.

Доступ до локального контексту (замикання / Closures): Лямбда-вираз може захоплювати та використовувати локальні змінні з методу, у якому він викликається (наприклад, змінну-лічильник або поріг фільтрації, введений користувачем).

4. У яких випадках власні утиліти на кшталт Map чи Filter корисно реалізувати самостійно, навіть якщо існує LINQ?
Контроль над негайним виконанням (Eager vs Deferred Execution): Стандартні оператори LINQ (Select, Where) використовують відкладене виконання (yield return), через що запит виконується заново при кожному переборі результату. Власний метод, що одразу повертає сформований список, гарантує одноразове обчислення та фіксацію результату в пам'яті.

Специфічна оптимізація продуктивності та пам'яті (Zero-allocation): У критичних до швидкодії ділянках коду (наприклад, ігрові рушії або високонавантажені сервіси) LINQ створює додаткові об'єкти-ітератори та замикання, що навантажує збирач сміття (GC). Власні утиліти можна оптимізувати під конкретні структури даних (наприклад, масиви або Span<T>) без зайвих алокацій пам'яті.

Додаткова вбудована логіка (логіювання, метрики, обробка помилок): Якщо під час обходу елементів потрібно автоматично логувати кожен крок, рахувати статистику оброблених елементів або перехоплювати специфічні винятки для окремих елементів колекції.

Робота в обмежених середовищах або для навчальних цілей: У мікроконтролерах, специфічних плагінах чи старих платформах без повної підтримки System.Linq, а також для глибокого розуміння того, як саме влаштовані методи розширення та делегати «під капотом».
